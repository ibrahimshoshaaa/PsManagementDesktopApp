# PSApp Flutter (Windows) — حالة المشروع

## تشغيل المشروع لأول مرة

```bash
flutter create . --platforms=windows   # لو مفيش مجلد windows/ لسه
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # لتوليد database.g.dart
flutter run -d windows
```

⚠️ **مهم:** `dart run build_runner build` **لازم** يتشغل قبل أي حاجة — ده اللي
بيولّد `lib/data/local/database.g.dart` (كود Drift المتولّد) اللي كل حاجة
تانية بتعتمد عليه. من غيره المشروع مش هيعمل build خالص.

هستخدم نفس بيئة GitHub Actions CI اللي عندك بالفعل في مشاريع Flutter
Windows التانية — لو عايز أظبطلك workflow مماثل قولي.

## كل الشاشات مبنية دلوقتي

- **تفعيل + تسجيل دخول** — كود المحل (شوب-كود) نفسه نظام الموبايل، أدمن/كاشير
  بنفس الـ hashes
- **مزامنة حقيقية** مع نفس Firebase بتاع الموبايل (REST + SSE — نفس البروتوكول
  حرفيًا: نفس الـ URLs، الأسرار، المسارات، منطق الـ patch الجزئي والـ debounce)
- **الأجهزة** — تشغيل/إيقاف مؤقت/استئناف/إنهاء مع حساب الفاتورة، أوردرات
  بوفيه، تنبيه بعد وقت معين، عد تنازلي لجلسة محددة، إلغاء الجلسة من غير حساب
- **التربيزات** — نفس منطق الأجهزة (تشغيل/إيقاف/إلغاء)، مع اختيار الحساب
  بالساعة أو بسعر اللعبة
- **تربيزات المشروبات** — أوردرات وحساب من غير مؤقت
- **السجل** — قائمة الجلسات المقفولة + إجماليات اليوم
- **المديونيات** — إضافة/سداد كامل/سداد جزئي/حذف (position-based من غير id،
  زي الموبايل بالظبط)
- **المصروفات** — إضافة/حذف بفئات
- **الإعدادات** — إضافة/حذف أجهزة وتربيزات وتربيزات مشروبات، الأسعار،
  الكاشيرز، المنيو وأقسام البوفيه، المخزون، اسم المحل، تفعيل الماتش/الشحن،
  كلمة سر الأدمن
- **لوحة التحكم** — إجمالي اليوم، صافي الربح، أجهزة/تربيزات شغالة، مديونيات
  مستحقة، الأكتر مبيعًا
- **البطولات** — تسجيل لاعبين، براكت إقصاء مباشر تلقائي (bye تلقائي لو العدد
  فردي)، اختيار فائز كل ماتش وتصعيد تلقائي، on-demand زي الموبايل
- **الشيفت** — بدء/إنهاء شيفت مع فحص قفل بين الأجهزة، ملخص إيراد عند الإنهاء
- **سجل التدقيق** — كل عملية مهمة بتتسجل fire-and-forget، شاشة عرض on-demand
- **الشحن** — كروت، شحن رصيد، استخدام كارت/شحن حر مع تسجيل في السجل
- **طلبات العملاء** — استقبال، تطبيق على الجهاز/التربيزة الصح تلقائيًا،
  تحديد كمنتهي
- **تصدير PDF/Excel** — تقرير يومي PDF (بالعربي)، وتصدير Excel للسجل/
  المصروفات/المديونيات، بيتحفظوا في مجلد `Reports` جنب التطبيق

كل حاجة فوق بتتزامن فورًا مع نفس Firebase بتاع الموبايل.

## GitHub Actions

فيه workflow جاهز في `.github/workflows/build-windows.yml`:
- بيشتغل على كل push/PR لـ main أو master، وبتقدر تشغّله يدوي (workflow_dispatch)
- بيعمل `flutter pub get` → `build_runner build` → `flutter build windows --release`
- بيرفع الناتج كـ artifact قابل للتحميل من صفحة الـ Actions
- لو عملت push لتاج بيبدأ بـ `v` (زي `v1.0.0`)، بيعمل GitHub Release تلقائي
  ويرفق ملف الـ zip عليه

```bash
git add .
git commit -m "Initial Flutter desktop rewrite"
git push origin main
# لو عايز Release: git tag v1.0.0 && git push origin v1.0.0
```

## نقاط تحتاج مراجعة قبل الإطلاق الفعلي

- `customer_orders` و`recharge_transactions`: الشكل مبني بناءً على قراءة
  الكود الفعلي في الموبايل، لكن يفضّل تتأكد بتجربة عملية إن الحقول متطابقة
  100% (خصوصًا لو فيه شاشات موبايل تانية بتكتب على نفس الـ path مش راجعناها)
- سجل التدقيق (`AuditLogService.log`) دلوقتي مربوط في: تشغيل/إنهاء/إلغاء
  الأجهزة والتربيزات، المديونيات، إضافة/حذف أجهزة وتربيزات من الإعدادات،
  الأسعار، الكاشيرز، اسم المحل، كلمة السر، تفعيل الماتش، بدء/إنهاء الشيفت.
  باقي الشاشات (بوفيه، مخزون، بطولات، مصروفات، شحن) لسه من غير audit logging
  — سهل تضيفه بنفس النمط
- إشعارات Telegram اللي في الموبايل (بتتبعت عند الشحن) — مش منقولة للديسكتوب،
  لو محتاجها قولّي وهضيفها
- المديونيات لو عايز id حقيقي بدل الاعتماد على ترتيب الـ array، لازم الموبايل
  يتحدّث معاها في نفس الوقت عشان التوافق يفضل قائم
- **لسه محتاج اختبار فعلي**: `flutter pub get` + `build_runner` +
  `flutter run -d windows` — الكود اتكتب بعناية لكن معنديش Flutter/Dart SDK
  في البيئة دي عشان أجربه بنفسي قبل ما أبعتهولك

## ملاحظات معمارية مهمة

- الـ Firebase schema (المسارات + الحقول) منقولة **حرفيًا** من
  `PsManagementMobileApp` — شوف `lib/data/remote/firebase_service.dart`
  للتفاصيل والتعليقات على كل مسار وكل دالة.
- Drift/SQLite هو مصدر الحقيقة المحلي؛ الـ SyncService هو الوحيد اللي بيتكلم
  مع Firebase مباشرة — أي controller تاني بيمر عليه.
- المديونيات في الموبايل من غير `id` (بتتعامل بالـ array position) — الجدول
  المحلي عنده `rowId` محلي بس للاستعلام، ما بيتبعتش لـ Firebase.
